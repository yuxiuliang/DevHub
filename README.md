# DevHub

本机、单用户的多 agent 协作台。

不是一个把终端平铺在一起的工具，而是**用一套你自己定义的流程，把几个异构 CLI 组织成一个小团队**：
一个需求一个会话，Planner 拆任务，成员各干各的（各自独立 worktree），Reviewer 初审，你终审，合并回主分支。

> 术语：界面上叫「会话」，代码和 API 里仍沿用 `room`。一个会话 = 一个需求 + 一组成员 + 一块任务看板。

## 快速开始

```bash
node server/index.js
```

打开 http://127.0.0.1:7373 。也可以用 `start.cmd`。

要求：Node >= 22.5（用了内置 `node:sqlite`，不需要 `npm install`，没有任何第三方依赖），以及 `git`。

## 支持的 worker

自动从 PATH 检测，检测不到会在左侧栏标灰：

| key | CLI | 非交互入口 |
| --- | --- | --- |
| `claude` | Claude Code | `claude -p ... --output-format stream-json` |
| `codex` | Codex CLI | `codex exec --json` |
| `opencode` | OpenCode | `opencode run --format json` |
| `agy` | Antigravity | `agy -p ... --output-format stream-json` |
| `dsh` | DeepSeek Harness | `dsh --profile headless --json` |

DevHub 只负责「什么时候、以什么身份、在哪个目录、拿什么上下文」去调用这些 CLI。
它不实现 runtime，不改这些 CLI 的配置，也不假设某个 CLI 只能做某类事——**角色是你写的，路由是你定的**。

### 需要额外凭据的 CLI

有些 CLI 需要环境变量（例如 dsh 的 headless profile 需要 `WORKBUDDY_API_KEY`）。DevHub 不保存、不展示密钥，只在启动子进程时合并以下来源：

1. 你自己启动 DevHub 的那个终端里已有的环境变量；
2. `.data/env.json`（可选，已加入 `.gitignore`）：

```json
{
  "WORKBUDDY_API_KEY": "…",
  "HTTPS_PROXY": "http://127.0.0.1:7890",
  "DEVHUB_DSH_PATH": "C:\\path\\to\\dsh.cmd",
  "DEVHUB_AGY_PATH": "C:\\path\\to\\agy.exe"
}
```

如果某个 CLI 不在 `PATH` 上（例如 dsh / agy），用 `DEVHUB_DSH_PATH` / `DEVHUB_AGY_PATH` 指定绝对路径；仓库里不内置任何人的本机路径。

`.data/env.json` 只用于解析 CLI 路径和给 agent 子进程补环境变量，不会写进数据库、日志或前端。

## 一次协作的流程

```
会话(需求) → 成员(角色) → 计划(Planner) → 任务 → worktree → 执行 → Diff → 评审 → 合并
```

1. **新建会话**：仓库路径可以点「浏览…」在本机目录树里选（会标出 git 仓库），也可以手动填写；然后填需求、成员。每个成员 = 名字 + 任意 worker + 你写的角色/职责 + 并发数。
   - 谁做 Planner、谁做 Reviewer 只是两个「位置」，不绑定 CLI。
   - 成员角色完全自由，系统零预设。
2. **生成计划**：Planner 输出 JSON 计划（任务、类型、负责人、验收、依赖）。**必须你确认后才落地**，可以在弹窗里改标题/说明/负责人/类型/验收，也能删任务或手工加任务。会话已经有执行记录时不允许重新应用计划，避免覆盖历史任务和旧分支冲突。
3. **开始执行**：就绪任务按依赖调度；每个任务自动开一个 git worktree + 分支 `devhub/<room>/<key>-<任务 id 后 6 位>`，agent 只在自己的目录里改。
4. **看 diff**：任务抽屉里有 Diff 标签，逐行高亮。
5. **评审**：Reviewer 对着 diff + 验收标准给出 `approve` 或 `request_changes`；打回的意见会带回给执行者，最多 2 轮。第 2 轮仍不通过就升级为「需人工」，不再自动评审，由你决定重跑后人工合并或取消。
6. **合并**：你点合并，squash 到基准分支。合并是串行的，且有未提交改动会拒绝。

## 关键设计

- **上下文隔离**：一个会话一个上下文；会话之间不共享对话、不共享 task、不共享 worktree。多个会话可以同时运行，互不串台。
- **共享什么**：会话需求、已生效的决策、上游任务摘要。Planner 和每个执行者都会拿到这些。
- **执行路径收敛**：Planner 的任务说明里即使写了原始仓库路径，下发给执行者时也会替换成该任务的 worktree 路径，并明确禁止读写工作目录之外的路径。
- **评审只读**：Reviewer 可以读 diff、跑测试，但不能改已跟踪文件或提交。评审前后会比对已跟踪文件的状态和 HEAD；测试产生的未跟踪临时文件不算改动，改动或提交则直接失败关闭，结论不予采用。
- **prompt 走文件**：写到 `.data/prompts/<runId>.md`，命令行只传一句固定指令，绕开 Windows 引号地狱。
- **并发**：全局 3、每会话 2、每成员默认 1；合并全局串行，不会有两个会话同时改基准分支。串行模式下每会话一次只跑一个。
- **可取消**：任务运行可以取消，计划和评审也能从会话顶部活动条点「停止」。取消后不会再提交半成品，也不会覆盖取消状态。
- **会话可维护**：顶部「设置」能改名、改需求、换计划者/评审者、增删成员、改角色/CLI/并发/模型，也能停用成员。停用成员不会被调度。已归档会话只读，恢复后才能继续。
- **归档不删数据**：归档只是把会话置为只读，任务、日志和 worktree 都保留；左侧「显示归档」可以随时找回来。
- **流程可编辑**：会话的「流程」标签是一个可拖拽画布（阶段节点 + 门禁 + 产物 + 回边上限）。
  点节点后在右侧用下拉框选「谁来做」、用复选框勾「通过后流向」；负责人可以留空，生成计划时 Planner 会按成员角色分配。
  产物只是可选标签，默认收在「高级设置」里，不选也不影响执行。有任务在跑时只读。
- **流程可复用**：新建会话时可以选「复制：某个会话」，把调好的流程整套带过去；也可以从起点模板里挑一个（通用协作 / 代码开发 / 文档撰写 / 调研分析 / 空白）。模板只是初始值，不绑定任务类型，创建后随便改。
- **数据全部本地**：SQLite 在 `.data/devhub.db`，日志在 `.data/logs`，worktree 在 `.data/worktrees`。
- **界面是实时的，不需要手动刷新**：
  - 服务端用 SSE 推送会话事件和 agent 输出，前端按事件增量更新；
  - 运行中的任务卡片直接显示「谁（成员 + CLI）· 跑了多久 · 当前在干什么」，例如 `阿蓝 · DeepSeek Harness  1:24  read src/cart.js`；
  - 成员条显示该成员正在跑的任务和最新动作；
  - 生成计划、自动评审这类不属于任务的运行，用会话顶部的活动条显示；
  - SSE 断线会自动重连，重连后补一次全量同步；右上角「实时 / 重连中」就是连接状态；
  - 5 秒轮询只在 SSE 断开时作为兜底，正常情况下不发任何轮询请求。

## 目录

```
server/
  index.js      HTTP 服务 + 静态托管
  api.js        REST API + SSE
  store.js      SQLite schema、流程起点模板、事件总线
  engine.js     会话 / 计划 / 任务 / worktree / 评审 / 合并 / 调度
  adapters.js   五个 CLI 的启动参数与事件解析
  prompts.js    Planner / 执行 / 评审的 prompt 契约
  git.js        worktree、commit、diff、squash merge
  fs.js         本机目录浏览（只读）
web/
  index.html    页面骨架
  app.js        看板、抽屉、计划弹窗、流程画布
  style.css     样式
```

## 已知限制（第一版）

- **worktree 隔离靠工作目录约束，不是 OS 沙箱**：DevHub 会收敛 prompt 里的路径并拒绝越界写入，但 CLI 本身仍有本机文件系统权限；不要给不受信任的 agent 开放敏感目录。
- **门禁字段目前只是标注**：画布上的 `human / agent / auto` 会显示在节点上并用于阶段归属，但评审和合并统一走任务抽屉里的按钮，还没有按门禁自动推进。
- **依赖在上游合并后才放行**：下游任务要等上游 `merged` / `done` 才会从 `backlog` 变成 `ready`。所以链式任务需要你逐个合并。
- 流程画布支持拖节点、改属性、增删阶段、保存；不支持在画布上直接拖线连边（默认顺序连边 + 评审回边）。
- 任务扇出（一个任务拆给多个成员并行）只留了数据结构，未实现。
- 上游任务失败时，下游会停在 `backlog`，需要你手动重试或取消。
- 没有鉴权、没有多用户，只监听 `127.0.0.1`。
- 只支持 git 仓库；不做非 git 目录。

## 第一次体验建议

1. 新建会话 → 填一个你自己的 git 仓库路径（或点「浏览…」选）。
2. 成员两个都用同一个 CLI（比如都选 dsh），角色分别写「实现工程师」和「评审」——这正是想验证的：**同一个模型，靠角色分工跑出协作**。
3. 生成计划 → 看一眼 Planner 拆得对不对，改一改再确认。
4. 开始执行 → 打开任务看日志和 Diff。
5. 点「自动评审」→ 看 Reviewer 的意见 → 通过或打回。
6. 合并 → 回仓库跑一次 `npm test`，确认真的修好了。

## 开发自检

- `npm run check`：所有服务端和前端文件的语法检查。
- `npm test`：git 集成测试（在系统临时目录建仓库，不碰你的项目）。
